# 3.3 — Reverse Proxy Configuration & Windows Desktop Client Fix

## Overview

This is the most technically complex part of the Nextcloud setup — but understanding *why* each step is needed makes it much easier to follow.

After the Cloudflare tunnel is live, the web browser and mobile apps will work fine. However, the **Nextcloud Windows Desktop Client** is significantly stricter. Without additional configuration, it will show a pink/red error screen and refuse to connect.

This document explains exactly what is happening and how to fix it permanently.

---

## Understanding the Problem — The HTTP vs HTTPS Mismatch

Here is what the system looks like from different perspectives:

```
External world sees:         Your Pi actually runs:
─────────────────────        ──────────────────────
https://cloud.justinnas.dev  http://localhost:7580
(Cloudflare provides HTTPS)  (plain HTTP internally)
```

The **web browser** is relaxed about this — it receives HTTPS from Cloudflare and is happy.

The **Windows Desktop Client** is strict — it connects at a deeper level and can detect that the server is actually speaking HTTP underneath. When it sees this mismatch, it interprets it as a potential security issue (a man-in-the-middle attack scenario) and throws a pink error screen.

**The solution has three parts:**
1. Tell Nextcloud via environment variables that it *is* running behind HTTPS
2. Tell Nextcloud to trust the Docker network gateway as a legitimate proxy
3. Clear the Windows app's cached failure state

---

## Part 1 — Environment Variables (The Permanent Fix)

### Why Environment Variables Instead of Editing `config.php` Directly?

The obvious approach would be to edit Nextcloud's configuration file (`config.php`) directly. This works initially but has a fatal flaw: **every time the Docker container restarts or updates, it can regenerate `config.php` from scratch**, wiping your manual edits.

Environment variables are injected into the Docker container at the engine level — they persist through container restarts, updates, and rebuilds. This is the correct, permanent approach.

### Adding the Environment Variables in CasaOS

1. Open **CasaOS** in your browser (`http://<PI-IP>`)
2. Click on the **Nextcloud** app to open its settings
3. Navigate to the **Environment Variables** tab
4. Add or modify the following three variables:

| Variable Name | Value | What it does |
|---------------|-------|-------------|
| `OVERWRITEPROTOCOL` | `https` | Tells Nextcloud: *"Even though you are running HTTP internally, all external links and auth tokens must use HTTPS"* |
| `OVERWRITEHOST` | `cloud.justinnas.dev` | Tells Nextcloud: *"Your public address is this domain — never leak the internal 192.168.x.x IP in links or redirects"* |
| `OVERWRITECLIURL` | `https://cloud.justinnas.dev` | Tells the **Cron background container**: *"Use this full URL when generating links in maintenance tasks"* |

> 📝 **Why is `OVERWRITECLIURL` needed separately?**  
> The Cron container runs background jobs (like sending email notifications or generating preview images). It has no browser connection — it generates URLs on its own. Without this variable, cron jobs would generate links pointing to `http://localhost:7580`, which would break email notifications and internal references.

5. Save the settings and **restart the Nextcloud container** for the variables to take effect

## Part 2 — Trusted Proxies (Preventing Accidental Lockouts)

### The Problem — The Brute Force Protection Trap

Nextcloud has a built-in security feature: if someone enters the wrong password too many times from the same IP address, it temporarily bans that IP to prevent brute-force attacks. This is a good feature — but it creates a serious problem in this setup.

**Here is what happens:**

```
Your Device (real IP: 203.x.x.x)
         │
         ▼
Cloudflare Tunnel
         │
         ▼
Docker Network Gateway (internal IP: 172.18.0.1)
         │
         ▼
Nextcloud Container
```

From Nextcloud's perspective, **every single user on the internet appears to come from `172.18.0.1`** — the Docker network gateway. Nextcloud cannot see the users' real external IPs through the tunnel.

**The consequence:** If any user types their password wrong a few times, Nextcloud bans `172.18.0.1` — the Docker gateway. This instantly locks **everyone** out of the NAS, including you, until you manually unban it from the command line.

### The Fix — Declare the Docker Subnets as Trusted Proxies

By telling Nextcloud *"these IP ranges are trusted proxy servers, not end users — look past them to find the real client IP"*, you solve two problems at once:
- Brute-force protection works correctly against real users' IPs
- The Docker gateway can never be accidentally banned

**Edit the Nextcloud config file:**

```bash
sudo nano /mnt/Web_Server/Nextcloud_Brain/html/config/config.php
```

Find the closing `);` at the end of the file and add the trusted proxies block **before** it:

```php
  'trusted_proxies' =>
  array (
    0 => '172.17.0.0/16',
    1 => '172.18.0.0/16',
  ),
```

The final lines of your `config.php` should look like this:

```php
  // ... other config entries above ...

  'trusted_proxies' =>
  array (
    0 => '172.17.0.0/16',
    1 => '172.18.0.0/16',
  ),
);
```

Save and exit: `Ctrl+X` → `Y` → `Enter`

> 📝 **Why `/16` instead of a specific IP like `172.18.0.1`?**  
> Docker dynamically reassigns container IP addresses every time containers restart or the system reboots. The gateway might be `172.18.0.1` today and `172.17.0.1` tomorrow. Using `/16` covers the entire Docker subnet range — so the trusted proxy declaration is always valid regardless of which IP Docker assigns.

> 📝 **What is `172.17.0.0/16` and `172.18.0.0/16`?**  
> These are Docker's internal private network ranges. `172.17.0.0/16` is Docker's default bridge network. `172.18.0.0/16` is typically used by Docker Compose stacks (like the Nextcloud multi-container stack). Both are included to be safe.

### Verify the Change

Restart the Nextcloud container so it picks up the config change:

```bash
sudo docker restart nextcloud
```

Then check the config was applied correctly:

```bash
sudo docker exec --user www-data nextcloud php occ config:list system | grep trusted
```

You should see both subnet entries listed.

## Part 3 — Clearing the Windows App Cache

Even with the server correctly configured, the Windows Desktop Client may still show the error — because it has a **local database** on your PC that caches the previous failed connection state. It is stuck in the failure and won't re-check.

**Steps to clear the cache:**

1. **Fully exit** the Nextcloud app — right-click the cloud icon in the **Windows system tray** (bottom-right, near the clock) and click **Quit**

2. Open the **Run** dialog:
   - Press `Win + R` on your keyboard
   - Type `%appdata%` and press **Enter**
   - This opens `C:\Users\YourName\AppData\Roaming\` in File Explorer

3. Find and **delete the `Nextcloud` folder** inside that directory

   > ⚠️ This deletes the app's local sync database and cached credentials. Your actual files on the NAS are **not affected** — only the local app state is cleared.

4. **Relaunch** the Nextcloud Desktop app from the Start Menu

5. When the setup wizard appears, enter:
   - Server address: `https://cloud.justinnas.dev`
   - Your username and password

The app should now connect cleanly without any pink screen error.

## Summary — What Each Fix Solves

| Fix | Problem it solves |
|-----|-----------------|
| `OVERWRITEPROTOCOL=https` | Nextcloud generates correct HTTPS links — Desktop Client accepts the connection |
| `OVERWRITEHOST` | Nextcloud never leaks local IP addresses in redirects or auth flows |
| `OVERWRITECLIURL` | Background cron jobs generate correct URLs for notifications and internal tasks |
| `trusted_proxies` | Docker gateway can never be accidentally banned — no mass lockout risk |
| Clear Windows app cache | Removes the stuck failure state so the client retries with a clean slate |
