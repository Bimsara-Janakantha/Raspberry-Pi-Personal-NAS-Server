# 2.1 — Storage Architecture & Disk Setup

## Overview

This NAS uses a **three-tier storage architecture** — three physically separate storage layers, each with a distinct job. This is a deliberate design decision, not just convenience.

| Tier       | Hardware            | Mount Point        | Role                                                    |
| ---------- | ------------------- | ------------------ | ------------------------------------------------------- |
| **Tier 1** | MicroSD Card (64GB) | `/` (root)         | Ubuntu OS bootloader & core system files only           |
| **Tier 2** | 1TB SATA HDD        | `/mnt/Web_Server`  | Docker engine, CasaOS, PostgreSQL database, Redis cache |
| **Tier 3** | 3 × 4TB SAS Array   | `/mnt/NAS_Storage` | Raw user file storage — nothing else                    |

### Why Three Tiers? — The SD Card Problem

A Raspberry Pi's MicroSD card is the most fragile component in any long-running Pi server build. SD cards have a limited number of **write cycles**. Nextcloud's PostgreSQL database writes constantly — logging every file access, session token, activity event, and background job result. If the database lived on the SD card, it would wear it out within months.

**The solution:** The SD card boots the OS and then hands off all heavy work to proper hard drives.

```
MicroSD Card          1TB HDD               3×4TB SAS Array
─────────────         ──────────────────    ──────────────────────────
Ubuntu kernel         Docker Engine         /mnt/NAS_Storage/
System services  →    CasaOS            →      ├── user1/ (x TB)
Bootloader            Nextcloud app            └── user2/ (y TB)
                      PostgreSQL DB
                      Redis Cache
                      (all wear here)       (all files here)
```

This means:

- The SD card only reads on boot — write cycles are essentially zero during normal operation
- The 1TB HDD takes all database wear — a standard HDD lasts tens of thousands of hours
- The 4TB array is a clean, dedicated file store with no OS contention

## Step 1 — Identify Your Drives

Before formatting anything, confirm which device path belongs to which physical drive.

```bash
lsblk
```

This lists every block device attached to the Pi. Identify your drives by their sizes:

**Example output:**

```
NAME        MAJ:MIN RM   SIZE RO TYPE MOUNTPOINT
mmcblk0     179:0    0  59.5G  0 disk            ← MicroSD Card (do not touch)
├─mmcblk0p1 179:1    0   512M  0 part /boot
└─mmcblk0p2 179:2    0    59G  0 part /
sda           8:0    0   931G  0 disk            ← 1TB HDD
└─sda1        8:1    0   931G  0 part
sdb           8:16   0   3.6T  0 disk            ← 3×4TB HDDs
└─sdb1        8:17   0   3.6T  0 part
sdc           8:32   0   3.6T  0 disk            ← 3×4TB HDDs
└─sdc1        8:33   0   3.6T  0 part
sdd           8:48   0   3.6T  0 disk            ← 3×4TB HDDs
└─sdd1        8:49   0   3.6T  0 part
```

> ⚠️ **Your device names (`sda`, `sdb`) may differ.** Always verify by size. Never format `mmcblk0` — that is your SD card and OS.

---

## Step 2 - Install the RAID Management Tool

Next, we need to install mdadm, which is the standard Linux utility for managing RAID arrays.

Run this command:

```Bash
sudo apt update && sudo apt install mdadm -y
```

---

## Step 3: Create the RAID 5 Array

🚨 STOP: In the command below, you MUST replace sdb, sdc, and sdd with the actual letters of your three 4TB drives that you found in Step 1!

Run the following command to bundle your three 4TB drives into a single virtual drive called md0:

```Bash
sudo mdadm --create --verbose /dev/md0 --level=5 --raid-devices=3 /dev/sdb /dev/sdc /dev/sdd
```

> (Type y and press Enter if it asks you to confirm).

---

## Step 4 — Format Both Hard Drives

> ⚠️ **This erases all data on the target drives.** Confirm the device paths from Step 1 before running these commands.

Format the **1TB Web Server drive**:

```bash
sudo mkfs.ext4 /dev/sda
```

Format the **RAID Storage Array**:

```bash
sudo mkfs.ext4 /dev/md0
```

`ext4` is used on both drives. It is the standard Linux filesystem, stable, well-supported, and — critically for the storage array — it supports kernel-level user/group quotas natively.

---

## Step 5 — Create the Mount Points

```bash
sudo mkdir -p /mnt/Web_Server
sudo mkdir -p /mnt/NAS_Storage
```

These are the directories the hard drives will be permanently attached to. Everything Docker, Nextcloud, and the database writes goes under `/mnt/Web_Server`. All user files go under `/mnt/NAS_Storage`.

---

## Step 6 — Find Both Drive UUIDs

Linux uses UUIDs (Universally Unique Identifiers) to identify drives in the boot configuration. Device names like `/dev/sda` can change if you add or remove drives — UUIDs never change.

```bash
sudo blkid
```

You will see output like this:

```
/dev/sda1: UUID="aaaa-1111-bbbb-2222-cccc3333dddd" TYPE="ext4"
/dev/md0: UUID="eeee-5555-ffff-6666-gggg7777hhhh" TYPE="ext4"
```

**Copy both UUID values.** You will need them in the next step.

---

## Step 7 — Configure Automatic Mounting at Boot

Edit the filesystem table so both drives mount automatically every time the Pi starts:

```bash
sudo nano /etc/fstab
```

Add these two lines at the **very bottom** of the file. Replace the placeholder UUIDs with the values you copied in Step 4.

```text
UUID=YOUR-1TB-UUID-HERE   /mnt/Web_Server  ext4  defaults                   0 2
UUID=YOUR-ARRAY-UUID-HERE /mnt/NAS_Storage ext4  defaults,usrquota,grpquota,nofail 0 2
```

> 📝 **What do the options mean?**
>
> | Option     | Drive            | Purpose                                             |
> | ---------- | ---------------- | --------------------------------------------------- |
> | `defaults` | Both             | Standard read/write mount                           |
> | `usrquota` | NAS Storage only | Track per-user disk usage for quota enforcement     |
> | `grpquota` | NAS Storage only | Track per-group disk usage                          |
> | `0`        | Both             | Exclude from `dump` backup utility                  |
> | `2`        | Both             | Run filesystem integrity check on boot (after root) |
>
> Notice that `usrquota` and `grpquota` are only needed on `/mnt/NAS_Storage` — that is the drive where per-user limits are enforced. The Web Server drive does not need quotas.

Save and exit: `Ctrl+X` → `Y` → `Enter`

---

## Step 8 — Mount All Drives

Apply the fstab changes immediately without rebooting:

```bash
sudo mount -a
```

Verify both drives mounted correctly:

```bash
df -h /mnt/Web_Server
df -h /mnt/NAS_Storage
```

Both should show their drive sizes with available space. If either command returns an error, double-check the UUID values in `/etc/fstab`.

---

## Verification Checklist

- [ ] `lsblk` correctly identified all three storage layers (SD, 1TB, array)
- [ ] Both drives formatted with `mkfs.ext4` without errors
- [ ] `/mnt/Web_Server` and `/mnt/NAS_Storage` directories created
- [ ] `sudo blkid` output captured — both UUIDs noted
- [ ] Both UUID lines added to `/etc/fstab` correctly
- [ ] `usrquota,grpquota` present **only** on the `/mnt/NAS_Storage` line
- [ ] `sudo mount -a` ran without errors
- [ ] `df -h` confirms both mount points show correct drive sizes
